System Architecture
Step-by-Step Request Flow
1

🔑 User Signs In

User clicks "Sign in with Google". Firebase Auth opens a popup, authenticates the user, and returns a session token to the frontend.

Firebase Auth → Google OAuth
2

📤 Upload Person Photo

User drops their photo on the person slot. Frontend sends it to POST /api/upload/person. Backend resizes it (max 1024px), saves it, then uploads it to Firebase Storage.

/api/upload/person → Firebase Storage
3

👗 Upload Outfit Photo

Same flow for the outfit image. Backend deduplicates by MD5 hash — if you upload the same image twice, it reuses the existing file. Returns a permanent Firebase URL.

/api/upload/outfit → Firebase Storage
4

💳 Credits Checked

Before generating, creditsService.js runs a Firestore transaction to check if the user has enough credits. Fast = 1 credit, Quality = 2 credits. New users get 10 free credits.

Firestore transaction → deductCredits()
5

🤖 AI Try-On Triggered

Frontend sends POST /api/generate with both Firebase URLs + chosen model. Backend downloads the images locally and calls the AI model via gradio_client.

/api/generate → image_service.py → HF Space
6

🔄 Model Fallback Chain

If the primary model is busy or fails (quota/rate limit), the backend automatically tries the next model. Falls back to a MOCK image only when all models fail.

CatVTON → WeShopAI → sm4ll → MOCK
7

💾 Result Saved

The generated try-on image is saved to backend/results/, then uploaded to Firebase Storage. The public URL is returned to the frontend and displayed instantly.

Result → Firebase Storage → URL to UI
8

💖 Save Look (Optional)

User clicks "Save Look". savedLooksService.js compresses all 3 images (person, outfit, result) to Base64 via Canvas and stores them permanently in Firestore — no expiry, no server dependency.

Firestore: users/{"{uid}"}/saved_looks
AI Model Fallback Chain

When /api/generate is called, models are tried in order. If a model fails (rate limit, quota, down), the next one is tried automatically.

Firebase Services Detail
🔐
Firebase Auth
Handles all authentication. Users sign in with Google via a popup. The frontend gets a UID and email that are used across all other Firebase services.
Google OAuth 2.0 popup
onAuthStateChanged() listener
🗄️
Firestore Database
NoSQL cloud database. Stores user data, credit balances, saved looks (as Base64 images), and admin audit logs. Images stored here survive server restarts forever.
users/{"{uid}"} → credits, totalGenerations
users/{"{uid}"}/saved_looks → Base64 results
admin_uploads → audit log
☁️
Firebase Storage
Cloud file storage for all image uploads and AI-generated results. Files are uploaded by both the frontend (via Pyrebase) and backend. Returns permanent public URLs.
uploads/ → person & outfit photos
results/ → AI try-on result images
Deployment
🚀
Platform — Render.com
Single web service. Python environment. Free tier with 15-min idle spin-down (handled by Keep-Alive).
gunicorn -w 4 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:$PORT --timeout 600 app:app
🏗️
Build Process
On deploy, Render installs Python deps, then builds the Vite frontend. The built JS/CSS is copied into backend/static/ and served by FastAPI at /.
pip install -r backend/requirements.txt
cd frontend && npm run build
💓
Keep-Alive System
Two layers of keep-alive pinging prevent idle shutdown. Backend pings itself every 10 min. Browser pings every 5 min while the app is open.
🐍 keep_alive.py → GET /api/ping (10 min)
🌐 pingService.js → GET /api/ping (5 min)
